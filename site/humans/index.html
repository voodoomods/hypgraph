For humans

Keep a record that tells you the truth about your evidence.

Whether you're 14 and growing cress, writing a thesis, or running a lab: write down what you think, what you'll do, what happened and what you conclude — and let the record work out how well each conclusion is actually supported.

Install

You need Python 3.10 or newer. HypGraph has no other dependencies.

pip install hypgraph

On a school or lab machine without admin rights, pip install --user hypgraph works too. Or skip installing altogether: the playground runs the real engine in your browser.

Five-minute tour

Build the teaching investigation that ships with HypGraph — how cholera was shown to spread through water in London in 1854 — and explore it.

hypgraph demo        # builds research.hypgraph and tells the story as it goes
hypgraph serve       # opens the Atlas explorer at http://127.0.0.1:8765
hypgraph report      # the facts of the investigation, generated from the record

As it builds, the demo tries three claims a hurried student (or an AI) would write, and shows you why the record refuses each. In the Atlas, click CL1, then Why to see what it rests on; click D1 — the decision to take the handle off the pump — to see why it's flagged REVISIT.

Your own investigation

Everything you write goes into one file (research.hypgraph, or --db yourfile). You write as --as name (or set HYPGRAPH_AUTHOR).

# 1. the question you're asking, and who will review your work
hypgraph init "Cress and light" --objective "Find out whether light colour changes how fast cress grows." --reviewers ada

# 2. what you think, and what would show it wrong
hypgraph add hypothesis statement="Blue light grows cress faster than red light." predictions='["Blue trays are taller after 7 days."]'

# 3. the plan, with what you expect BEFORE you measure
hypgraph add experiment aim="Grow cress under blue and red light for a week." \
  protocol="Two trays under each colour, same soil, water and temperature; measure 20 seedlings per tray on day 7." \
  success_criteria="A height difference larger than the difference between trays of the same colour."
hypgraph link X1 tests H1 expected="Blue trays are taller than red trays on day 7."

# 4. what happened
hypgraph add result summary="Blue trays averaged 41 mm, red trays 33 mm after 7 days." values='{"blue_mm": {"value": 41}, "red_mm": {"value": 33}}'
Why write the expectation first? If you only decide what counts as success after you've seen the data, any result can be made to look like a success. HypGraph won't link an experiment to a hypothesis with tests unless you say what you expect (expected=…).

Claims that pass

A claim is what you say you now know. The record checks it as you write it:

  • Link the evidence — a supports link from the result, with a reason.
  • Say where it holds — the scope: which samples, which method, which conditions.
  • Bind every number — each number in the statement must come from a result field (a measurement), from the scope, or from the investigation's stated constants.
  • No absolutes you haven't earned — "always", "never", "proves" need a count where it happened in all (or none) of the trials.
hypgraph add claim statement="Blue-lit cress averaged 41 mm against 33 mm under red light." \
  scope="Two trays each, one week, a windowless room." \
  measurements='[{"name": "blue", "result": "RS1", "key": "blue_mm", "value": 41}, {"name": "red", "result": "RS1", "key": "red_mm", "value": 33}]' \
  --link "supports:from:RS1:the tray heights are the measurement"

If something's wrong, the record says what, in words — fix it and try again. Try a few wrong ones in the playground.

Reviews

Only the reviewers you named can make a claim checked — and never on their own work. Anyone else's review is kept as a comment. If you change a claim after it was checked, the check goes stale: the reviewer looks again.

hypgraph --as ada review CL1 pass --method "Re-measured the trays." --notes "41 and 33 hold."
hypgraph show CL1 --why       # what it rests on
hypgraph show RS1 --impact    # what would break if this result were wrong
hypgraph work                 # what's waiting: reviews, revalidations, disputes

In Python & notebooks

from hypgraph import Graph, Policy

g = Graph("cress.hypgraph", policy=Policy(reviewers={"ada"}))   # Graph() keeps it in memory
sam = g.author("sam")
inv = sam.investigation("Cress and light", "Find out whether light colour changes how fast cress grows.")["id"]
r = sam.add("result", inv, summary="Blue trays averaged 41 mm, red trays 33 mm after 7 days.",
            values={"blue_mm": {"value": 41}, "red_mm": {"value": 33}})
c = sam.add("claim", inv, statement="Blue-lit cress averaged 41 mm against 33 mm under red light.",
            scope="Two trays each, one week, a windowless room.",
            measurements=[{"name": "blue", "result": r["id"], "key": "blue_mm", "value": 41},
                          {"name": "red", "result": r["id"], "key": "red_mm", "value": 33}],
            links=[{"rel": "supports", "from": r["id"], "why": "The tray heights are the measurement."}])
print(c["state"]["sentence"])
print(g.report(inv)["markdown"])

When you compute something, hash the files with hypgraph.file_sha256(path) and record a run that uses your data and produced your result — then anyone can tell whether two results share data (and so count as one line of evidence, not two).

For teachers

HypGraph makes the method visible, so you can grade it.

  1. Set up. Each student (or group) keeps their own file. You're the reviewer: hypgraph init "…" --objective "…" --reviewers ms-lee.
  2. Predict before measuring. Ask for hypotheses with predictions and an experiment with expected outcomes before any data is collected. The record timestamps it all and can't be backdated.
  3. Let the record push back. Students will try "this proves…" and numbers from nowhere. The refusals explain the problem better than a red pen, at the moment it matters.
  4. Collect. Students hand in hypgraph export -o name.bundle.json. hypgraph verify (or hypgraph.com/verify) shows it wasn't edited afterwards; open it in the Atlas to read it.
  5. Review. Your pass, objection or fail becomes part of their record — and a student who revises a claim sends it back to you automatically.

Start with the Broad Street case (hypgraph demo): it shows competing hypotheses, a decisive experiment, a skeptic who replicates, and a decision that has to be revisited — in an hour of class.

Publishing with a paper

  1. Keep the study in a graph of its own, with its reviewers named.
  2. Record runs with hashed code and data; bind every claim's numbers to results.
  3. When you submit, hypgraph export -o study.bundle.json and put the bundle's head hash in the paper (or a preregistration, or a repository tag). That anchors it: a later bundle can't have rewritten anything before that hash.
  4. Generate the facts section with hypgraph report -o facts.md. Write your interpretation below it.
  5. Referees run hypgraph verify study.bundle.json, or drop it on /verify, and explore it in the Atlas.

Reading the standing

Every node carries one honest sentence, for example:

active claim · checked (whitehead:checked, v2) · 2 independent lines of support · replicated on new data · no external replication
  • checked / unchecked / contested / review stale — reviews by the named reviewers, on this version.
  • independent lines — supports that don't share a run, data or a source.
  • evidence — the strongest line: unverified report → agent-reported run → lab-recorded run → reproduced in project → separate implementation → replicated on new data → external source.
  • AT RISK — something it rests on was withdrawn or contested. REVISIT — a decision whose basis changed. UNSUPPORTED — every support it had has fallen.

Questions

Is my data sent anywhere?

No. HypGraph is a library and a file on your computer. The website's playground and verifier run in your browser.

Can I edit something I got wrong?

Yes — by adding a new version (hypgraph revise) or withdrawing it (hypgraph withdraw). The old version stays on record. That's the point: the history of how you got there is part of the evidence.

Can someone fake a record?

Anyone can write a file. What they can't do is change one after its head hash was published without the change showing. See anchoring.

Why so strict about numbers?

Because the most common way a summary goes wrong is a number that matches no result — copied wrong, rounded wrong, remembered wrong, or invented. The check is mechanical, so it never gets tired.
